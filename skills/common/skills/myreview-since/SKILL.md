---
name: myreview-since
description: 审查指定提交及其之后的全部改动，输出修改总结与分级问题清单（逻辑/业务功能/严重性能/强烈推荐重构）。Use when the user asks to review 提交/commit X 及其之后的修改, or says 类似「review提交20014d74 及其之后的总修改」的语句, or names a commit hash and asks to review everything after it.
---

以提交 `<COMMIT>`（含其自身）到 `HEAD` 的全部改动为审查对象，聚焦逻辑、业务、性能与重构，最终交出一份可定位的总结与问题清单。

## 1. 确定审查范围

**默认**：用户给出提交哈希（如 `20014d74`，可被截断）时，审查**该提交及其之后的全部改动**（含首提交自身）。

**用户有明确说明时，按说明执行**，说明优先级高于默认。常见覆盖：

- 「审查暂存区」→ `git diff --cached`
- 「审查工作区」/未暂存改动 → `git diff`
- 「只审查这个提交」→ `git show <COMMIT>`（或 `git diff <COMMIT>^ <COMMIT>`）
- 「审查 A..B」/两个哈希 → 所给区间
- 「审查最近 N 个提交」→ `HEAD~N..HEAD`

用户未提供任何范围、也无法推断时，向用户询问后再继续。不要猜测。

完成标准：拿到一个明确的范围（基线 + 终点）。

## 2. 核对范围

按步骤 1 选定的范围取提交列表与统计，例如默认的「提交及其之后」含首提交自身，基线取其父提交：

```
git log --oneline <COMMIT>^..HEAD
git diff --stat <COMMIT>^..HEAD
```

首提交是根提交（无父）时，改用 `<COMMIT>..HEAD` 并把根提交单独一并纳入。整个范围核对：`<COMMIT>` 是否在本次范围内、范围内提交数是否与 diff 一致。

完成标准：确认基线、范围内的提交列表与变更文件清单。

## 3. 精读改动

```
git diff <范围> -- <file>
```

逐文件阅读。**不要只看 diff**：打开改动所在的完整文件理解上下文，按需 `grep` 全部调用点，并按逻辑调用链串起数据流（输入→处理→输出/落库）。改动涉及跨文件契约时，两端都要看。

完成标准：每个改动文件都已读；每处改动的上下游调用链已确认。

## 4. 分类审查

对每个改动点，逐条套用四类检查：

- **逻辑问题**：条件/边界/空值/Off-by-one、状态机与并发（锁、竞态、重入）、错误被吞或错误地向上传播、资源未释放、单位/精度/时区、幂等性等。
- **业务功能问题**：是否满足需求意图、是否破坏既有行为、是否与文档或注释承诺一致、不变量是否被破坏，是否与业界知识、行为明显不一致又没有注释说明等。
- **严重性能问题**：热路径上的全表扫描/逐行查询、无界内存增长、O(n²)、锁粒度过大、循环内 I/O 或阻塞调用、每帧/每次回调重复构造、编译等。
- **强烈推荐重构**：可用更简单实现替代的复杂逻辑、重复代码、明显劣于业务惯用法、错误的抽象层次、兼取 YAGNI 检查是否本就不该写等。

每条问题必须给出 `file_path:line` 定位、触发条件、后果、以及最小修复方向。只报有实际影响的问题，不报风格偏好。

完成标准：每个改动点都经过四类检查；每条问题都可定位且说明了影响。

## 5. 输出

按以下结构输出，中文：

```
## 审查范围
<COMMIT> (日期) 起，共 N 个提交，X 文件 +Y/-Z
<git log --oneline 列表>

## 修改内容总结
（按功能/模块分组，逐项说明改了什么、为什么）

## 问题清单
### 逻辑问题
- [file_path:line] 现象 / 触发条件 / 影响 / 建议
### 业务功能问题
### 严重性能问题
### 强烈推荐重构

## 结论
（整体风险判断：可合入 / 需修复后合入 / 需重做，及最紧要的 1~3 项）
```

无问题的分类写「无」。总结与问题清单一并给出，不要只列问题。

完成标准：四类清单齐备，总结覆盖全部改动文件，结论明确。
