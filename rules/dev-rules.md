## 编码规范
- 单文件建议不超过 1000 行，单文件硬上限为 2000 行；超过 2000 行的文件必须拆分，除非是生成代码、测试数据、协议定义、常量表、既有缺陷文件等例外，并应标注原因，能改进时提出推荐方案供决策。
- AI 在修改代码时，如果会导致文件超过硬上限，不应直接向该文件追加逻辑，而应优先拆分模块。
- 拆分应按职责、领域或功能边界进行，不要机械地按类型拆。
- 封闭、有限、互斥的值集合优先使用 enum；开放集合、可组合选项或纯布尔语义不要强行使用 enum

## 核心链路测试规范
- 核心链路必须有可重复稳定的自动化测试覆盖；优先系统级/端到端测试，当前无法做到时至少要有集成测试并记录补齐计划。
- 核心链路测试必须覆盖：
  - 正常主流程
  - 关键错误路径
  - 重要边界条件
- 系统级测试必须可重复稳定执行：
  - 不依赖公网或真实第三方服务
  - 不依赖未固定的时间、随机数、执行顺序
  - 不依赖共享可变状态
  - 使用临时目录/随机端口/隔离数据库或测试容器/使用固定种子/固定 fixture/隔离测试数据

## 代码注释规范
- 注释使用中文，日志使用中文或英文
- 不在代码行末尾添加注释
- 公共API必须提供简洁明了的doc
- 代码自解释优先，避免冗余注释
- 复杂逻辑、特殊做法、取舍必须有注释
- 表、表字段、struct及其字段必须有注释

## 日志规范
1. **必须记录日志的场景**
   - 任何数据的创建、更新、删除操作。
   - 应用内异常创建。
   - 应用外异常（如数据库、网络、第三方SDK异常）被捕获并转换为应用内异常的时刻。

2. **禁止记录日志的场景**
   - 同一应用内异常在上层调用链中重复记录；仅在异常最初被创建/抛出的位置记录一次，避免反复打印。

3. **日志内容要求**
   每条日志必须包含以下可定位及可区分的关键信息：
   - **定位对象**：事件发生的业务对象标识（如订单ID、用户ID、设备ID）。
   - **核心事件**：如“创建订单”、“扣减库存”、“XX异常”，关键参数或状态变化摘要。
   - **异常原因**：若为异常日志，需包含异常类型、根本原因描述及上下文（如输入参数、当前状态）。
   - **区分性**：确保不同日志条目可明确区分，不产生歧义。
   - **必要性**: 避免无法增加有效信息的内容（如固定的“操作成功”）。
4. **敏感信息脱敏**
   日志中严禁明文记录敏感字段，必须脱敏处理，如：
   手机号、身份证号、银行卡号、密码、Token、密钥等。
   脱敏方式示例：遮盖中间位（`138****1234`）、替换为哈希值。

5. **异常处理与日志配合**
   - 明确区分**应用内异常**（自定义业务异常）和**应用外异常**（如标准库、第三方库异常）。
   - 所有应用外异常**必须被捕获并转换为应用内异常**，在捕获转换点记录日志（包含原始异常消息和关键堆栈），防止信息被吞。
6. **日志级别建议**
   - 数据变动：INFO
   - 业务异常：WARN
   - 系统/外部异常：ERROR

## 工具选择：LSP vs 搜索
1. **按问题类型选工具**
   - 类型、文档、签名、跳转定义、符号定位 → LSP：`hover` / `goToDefinition` / `workspaceSymbol` / `documentSymbol`
   - 按内容找文件、列结构、找调用点 → `grep` / `glob`
2. **各归各位**
   - 不拿 LSP 当搜索用，也不用 grep 猜类型。
3. **`findReferences` 限制**
   - 只在需要精确到宏 / re-export 时使用；查热门符号会返回上千行，改用 grep 搜调用点。
4. **冷启动**
   - LSP 启动中请求可能返回空（rust-analyzer 正在索引），空结果先重试一次再下结论。

## Git 操作规范
- AI 修改代码后不得主动执行 `git add` / `git commit`，仅在用户明确要求时才提交
